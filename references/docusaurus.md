# Docusaurus Reference

Use this reference when initializing, repairing, structuring, styling, validating, or building the human-facing documentation site.

This skill targets an office/restricted environment. **Prefer the Docusaurus version and packages already approved/available in the target repository/environment. Do not upgrade dependencies merely to match public examples.** Public documentation is guidance; the installed version/package lock is authoritative for exact syntax.

## Objectives

The Docusaurus layer should:

- present the canonical Markdown/MDX clearly to humans
- remain simple enough for future engineers to maintain
- support progressive module -> capability -> flow navigation
- render useful Mermaid diagrams
- build reliably in the restricted environment
- avoid becoming a custom frontend application

## Setup Strategy

### Existing site

If a Docusaurus site already exists:

1. inspect `package.json` and lockfile
2. inspect `docusaurus.config.*`
3. inspect `sidebars.*`
4. inspect `src/css/custom.css` and any swizzled/custom theme components
5. run the existing build command before changing infrastructure
6. preserve working conventions unless they prevent the required documentation

Do not reinitialize a working site.

### New site

If no site exists:

1. use the approved/local Docusaurus package source/version
2. initialize under `documentation/`
3. keep the starter minimal
4. enable docs and Mermaid only as needed
5. run a build immediately
6. do not start mass content generation until the shell builds

If packages are unavailable in the restricted environment, stop and ask the user to configure/provide Docusaurus dependencies.

## Sidebar Strategy

The sidebar must represent the **business/system hierarchy**, not Java packages or microservice directories.

Prefer filesystem structure that mirrors the intended navigation when autogenerated sidebars are practical. Docusaurus supports both explicit and autogenerated sidebars; choose the simplest maintainable option for the installed version.

Example:

```text
System Overview
Modules
  Outward Clearing
    Overview
    Architecture
    Business Flows
      Ingestion
      Clearing Processing
      Return Processing
    Status Model
    Data Model
    Batch Jobs
    APIs
    Integrations
    Testing
    Operations
Documentation Coverage
Developer Reference
```

Use front matter such as `sidebar_position`, `sidebar_label`, stable `id`/`slug`, or category metadata only when useful. Avoid fragile manual ordering across hundreds of pages.

## Mermaid

Docusaurus supports Mermaid through its Mermaid theme/configuration in supported versions. For the installed version, follow its matching Docusaurus documentation/package conventions.

Typical modern configuration uses:

```js
export default {
  markdown: {
    mermaid: true,
  },
  themes: ['@docusaurus/theme-mermaid'],
};
```

Do not copy this blindly if the installed Docusaurus major/version uses different configuration syntax.

Use Mermaid for:

- system/module architecture
- business/process flows
- sequence diagrams
- state transitions
- ER/data relationships
- service/integration dependencies

### Diagram rules

- One diagram should answer one clear question.
- Split large flows into overview + child diagrams.
- Keep node labels short; link/explain details in prose/tables.
- Do not encode unverified transitions.
- Show `UNKNOWN`/`OUT_OF_SCOPE` boundaries explicitly when material.
- Prefer left-to-right for long process flows when it improves readability.
- Prefer state diagrams for lifecycle/status behavior and ER diagrams for important relationships.

### Semantic visual vocabulary

Use a consistent palette through Mermaid theme variables/classes or site CSS. Exact colors may follow organizational branding, but meaning must stay consistent:

- normal processing/component
- decision/branch
- external integration
- successful terminal state
- failure/error
- unknown/conflict
- out-of-scope boundary

Never rely on color alone; labels/icons/borders/text must preserve meaning in dark mode and for accessibility.

## Markdown / MDX

Default to `.md` for ordinary documentation. Use `.mdx` only when React/Docusaurus components materially improve the page.

Useful built-in patterns include:

- headings and tables
- admonitions for warnings, unknowns, operational notes and evidence caveats
- details/summary for secondary technical depth
- tabs only when comparing meaningful variants/environments
- code blocks for payloads/configuration/examples
- Mermaid code blocks for diagrams

Avoid turning every page into MDX. Plain Markdown is easier for agents, notebooks, Git diffs and future migrations.

## Progressive Disclosure

A module overview should not contain every implementation detail.

Recommended navigation:

```text
System
  -> Module overview
      -> Capability/flow
          -> Subflow
              -> Job/API/status/table/integration detail
```

Overview pages answer "what is this and how does it fit?" Detailed pages answer "how exactly does this work?"

For large flows, use a high-level Mermaid diagram with links to child pages rather than one enormous graph.

## Reusable Components

Before creating React components, ask whether standard Markdown/Docusaurus/Mermaid can express the information clearly.

Custom components are justified when the interaction is repeated and materially useful, for example:

- StatusExplorer
- VariantComparison
- FlowStepCard
- EvidenceBadge
- CoverageBadge

Keep component APIs data-driven and small. Do not embed business truth only inside React source; canonical facts must remain readable in Markdown/data accessible to agents.

Avoid custom components for one-off decoration.

## Styling

Prefer a small `custom.css` layer over extensive theme swizzling.

Priorities:

1. readable typography and spacing
2. clear hierarchy
3. usable tables/code blocks
4. Mermaid readability
5. semantic badges/callouts
6. light/dark mode compatibility
7. responsive layout

Do not trade maintainability for visual novelty. Animations should be subtle and optional; core documentation must work without them.

## Evidence Presentation

Human pages should be readable without provenance noise on every sentence, but important technical claims should remain traceable.

Useful patterns:

- a small "Implementation references" section
- source paths/symbols in technical tables
- evidence badges for uncertain/high-risk facts
- explicit admonitions for `UNKNOWN` and `CONFLICT`

Never hide uncertainty to make a page visually cleaner.

## Agent Entry Point

Maintain a small `documentation/AGENT_INDEX.md` (or equivalent existing convention) that links to the same canonical docs.

It should contain:

- system name/purpose
- approved module map and coverage
- links/paths to module overview docs
- glossary/reference locations
- checkpoint/resume path
- instructions to respect `OUT_OF_SCOPE`, `UNKNOWN` and `CONFLICT`

Do **not** duplicate the entire documentation into a separate agent-only tree.

## Build Discipline

Use the repository's existing package manager and scripts.

Required checks:

1. baseline build before major infrastructure changes when possible
2. build after initial setup
3. build after config/sidebar/theme structural changes
4. final production build after content generation

Treat these as defects:

- invalid MD/MDX
- invalid Mermaid
- broken internal links
- broken sidebar/category references
- missing assets
- compile/runtime errors introduced by custom components

Do not claim success merely because files were generated.

## Official References

When internet access is available, prefer the current official Docusaurus documentation at `https://docusaurus.io/docs` and match guidance to the installed major/version. Particularly relevant topics:

- configuration (`docusaurus.config.js` / `.ts`)
- docs/plugin configuration
- sidebars and autogenerated sidebars
- Markdown/MDX features
- Mermaid diagrams / `@docusaurus/theme-mermaid`
- front matter

In restricted/offline environments, rely on the installed package/version, existing working project conventions, local package documentation if available, and this reference. Do not attempt an internet-dependent upgrade.
